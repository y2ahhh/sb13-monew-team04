# MID4-244 API 실패 경계 상세 결과

> [MID4-244 요약](README.md) · [측정 조건과 재현 방법](measurement-and-reproduction.md) · [활동내역 성능 문서 통합 안내서](../activity-history-performance-guide.md)

이 문서는 부분 커버링 인덱스를 적용한 데이터 몰림 조건과 기존 인덱스를 사용한 일반 데이터 조건의 API 회차별 결과, 요청당 집계량과 해석의 한계를 기록한다.

## 한눈에 보기

- 후보 인덱스를 적용한 데이터 몰림 조건은 `250 rps`까지 3회 모두 통과했고, `275 rps`는 변동 구간, `300 rps`는 반복 실패였다.
- 데이터 몰림 2배 조건은 후보 인덱스를 사용해도 `200 rps`의 첫 1분부터 p95 `2,094.53 ms`, p99 `2,185.07 ms`로 실패했다.
- 일반 데이터는 `300 rps · 10분`을 통과했지만 `350 rps · 10분`은 요청이 누적되며 실패했다.
- 모든 결과는 로컬 Docker, 단일 대상 사용자와 워밍업된 캐시를 사용한 측정값이며 운영 보장값이 아니다.

## 요청당 집계량과 실패 원인

대표 실행계획에서 디스크 읽기(`shared read`)는 모두 `0`이었다. 워밍업 뒤 메모리에 올라온 같은 조건을 비교했으므로 처음 디스크에서 읽는 시간이 결과에 섞이지 않았다.

후보 인덱스를 사용한 집계는 대부분 인덱스만 읽는 방식(Index Only Scan)으로 바뀌었다. 하지만 최근 조회 기사 하위 조회는 결과 10건마다 두 집계를 실행하고, 구독 관심사 하위 조회는 결과 50건마다 집계를 실행했다. 데이터 몰림 2배 조건에서 집계 1회가 확인한 행 수는 기사별 조회 수 계산 약 `20,003건`, 관심사별 구독자 수 계산 약 `2,011건`이었다.

데이터 몰림 2배 조건의 실행계획 원문에 기록된 집계 단계는 다음과 같다. 기존 인덱스 상태의 `Index Scan`에는 `Heap Fetches` 항목이 따로 표시되지 않으며 실제 테이블을 읽는다.

| 집계 단계 | 집계 1회당 확인한 행 수 | 반복 횟수 | 공유 버퍼(기존 → 후보 인덱스) | 후보 인덱스 Heap Fetches |
| --- | ---: | ---: | ---: | ---: |
| 최근 작성 댓글의 좋아요 수 | 2,001 | 10 | 489 → 170 | 0 |
| 최근 좋아요한 댓글의 좋아요 수 | 2 | 10 | 50 → 31 | 0 |
| 최근 조회 기사의 댓글 수 | 2,002 | 10 | 3,520 → 180 | 10 |
| 최근 조회 기사의 조회 수 | 20,003 | 10 | 4,299 → 1,250 | 0 |
| 구독 관심사의 구독자 수 | 2,011 | 50 | 2,969 → 756 | 0 |

후보 인덱스를 사용한 대표 실행계획의 `rows × loops`를 계산하면, API 요청 한 번이 집계 때문에 확인한 인덱스 항목 수를 비교할 수 있다. 이 값은 SQL 실행 시간 자체가 아니라 하위 조회가 반복해서 센 데이터 양이다.

| 집계 단계 | 데이터 몰림 조건 `rows × loops` | 데이터 몰림 조건 항목 수 | 데이터 몰림 2배 조건 `rows × loops` | 데이터 몰림 2배 조건 항목 수 | Heap Fetches 변화 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 최근 작성 댓글의 좋아요 수 | 1,001 × 10 | 10,010 | 2,001 × 10 | 20,010 | 0 → 0 |
| 최근 좋아요한 댓글의 좋아요 수 | 2 × 10 | 20 | 2 × 10 | 20 | 0 → 0 |
| 최근 조회 기사의 댓글 수 | 1,002 × 10 | 10,020 | 2,002 × 10 | 20,020 | 0 → 10 |
| 최근 조회 기사의 조회 수 | 10,003 × 10 | 100,030 | 20,003 × 10 | 200,030 | 0 → 0 |
| 구독 관심사의 구독자 수 | 1,011 × 50 | 50,550 | 2,011 × 50 | 100,550 | 0 → 0 |
| **합계** |  | **170,630** |  | **340,630** |  |

특정 대상에 추가한 좋아요·댓글·조회·구독 건수를 데이터 몰림 조건의 2배로 늘리자 요청 한 번에 확인한 인덱스 항목도 약 `17.1만 개`에서 `34.1만 개`로 거의 2배가 됐다. `200 rps`가 계속 들어온다고 단순 환산하면 초당 약 `3,413만 개`에서 `6,813만 개`를 확인하는 양이다. 대부분 `Index Only Scan`과 `Heap Fetches 0`을 달성했으므로 실제 테이블 재방문은 줄었지만, 정확한 개수를 구하기 위해 조건에 맞는 인덱스 항목을 세는 일은 사라지지 않았다.

## API 실패 경계 결과

### 데이터 몰림 조건, 200 rps

| 인덱스 상태 | 측정 | p95 ms | p99 ms | 요청 누락 | 오류율 | 판정 |
| --- | --- | ---: | ---: | ---: | ---: | --- |
| 기존 인덱스 | 1분 1회차 | 116.76 | 149.70 | 0 | 0% | 통과 |
| 기존 인덱스 | 1분 2회차 | 164.24 | 240.89 | 0 | 0% | 통과 |
| 기존 인덱스 | 1분 3회차 | 383.78 | 643.91 | 0 | 0% | 실패 |
| 후보 인덱스 | 1분 1회차 | 43.23 | 72.82 | 0 | 0% | 통과 |
| 후보 인덱스 | 1분 2회차 | 30.78 | 34.84 | 0 | 0% | 통과 |
| 후보 인덱스 | 1분 3회차 | 31.37 | 36.09 | 0 | 0% | 통과 |
| 후보 인덱스 | 10분 지속 | 42.28 | 53.46 | 0 | 0.005% | 통과 |

기존 인덱스는 3회 가운데 값이 p95 `164.24 ms`, p99 `240.89 ms`라서 가운데 값 기준으로는 통과했다. 그러나 3회차가 기준을 넘었으므로 안정적으로 통과했다고 보기는 어렵다. 후보 인덱스는 1분 3회와 10분 지속 측정을 모두 통과했다.

### 데이터 몰림 조건, 요청량 상향 측정

후보 인덱스를 적용한 데이터 몰림 조건에서 `200 rps`부터 요청량을 높였다. 표에는 각 RPS의 세 회차 원본 값을 순서대로 적었다.

| RPS | p95(ms) 1·2·3회차 | p99(ms) 1·2·3회차 | 요청 누락 1·2·3회차 | 판정 |
| ---: | --- | --- | --- | --- |
| 200 | 77.26 / 33.18 / 36.39 | 196.72 / 40.64 / 46.43 | 0 / 0 / 0 | 3회 통과 |
| 205 | 37.69 / 36.71 / 39.10 | 46.45 / 43.72 / 49.38 | 0 / 0 / 0 | 3회 통과 |
| 210 | 37.67 / 37.54 / 39.77 | 45.79 / 46.50 / 50.06 | 0 / 0 / 0 | 3회 통과 |
| 225 | 42.05 / 40.80 / 44.86 | 58.30 / 51.19 / 64.04 | 0 / 0 / 0 | 3회 통과 |
| 250 | 48.32 / 47.04 / 49.88 | 69.77 / 67.31 / 65.79 | 0 / 0 / 0 | 3회 통과 |
| 275 | 1,499.57 / 148.66 / 52.24 | 1,780.70 / 280.41 / 74.63 | 1 / 0 / 0 | 가운데 값 기준 통과, 변동 있음 |
| 300 | 1,703.82 / 1,964.78 / 1,906.99 | 1,872.36 / 2,113.26 / 2,099.26 | 78 / 449 / 388 | 3회 실패 |

이번 측정에서 세 번 모두 통과한 가장 높은 요청량은 `250 rps`였다. `275 rps`는 가운데 값 p95 `148.66 ms`, p99 `280.41 ms`가 기준 안이고 3회 중 2회가 통과했으므로 가운데 값 기준 통과 지점이다. 다만 한 회차는 응답 시간과 요청 누락 기준을 넘었으므로 안정적인 보장값은 아니다. `300 rps`는 세 회차 모두 실패했다. 따라서 `250 rps`는 안정 통과, `275 rps`는 변동이 있는 통과, `300 rps`는 반복 실패로 구분한다.

MID4-227과 같은 데이터 몰림 조건이 적용됐는지 추가 건수를 확인했다.

| 확인 항목 | 건수 |
| --- | ---: |
| 최근 댓글 10개의 추가 좋아요 | 10,000 |
| 최근 기사 10개의 추가 댓글 | 10,000 |
| 최근 기사 10개의 추가 조회 | 100,000 |
| 관심사 50개의 추가 구독 | 50,000 |

첫 워밍업은 p95 `56.71 ms`, p99 `145.64 ms`였고, 상향 측정 재개 전 워밍업은 p95 `48.17 ms`, p99 `152.06 ms`였다. 두 워밍업 모두 오류와 요청 누락이 없었다. PostgreSQL 컨테이너의 누적 블록 읽기는 `200 rps` 시작 전부터 `300 rps` 종료 후까지 `258 kB`로 같았다. 이 값만으로 모든 계층의 캐시를 증명할 수는 없지만, 부하 측정 중 새 디스크 읽기가 관찰되지 않았다는 근거다. SQL 실행계획에서도 워밍업 후 `shared read=0`을 확인했으므로 이번 결과에는 처음 디스크에서 읽는 시간이 섞이지 않은 것으로 본다.

### 데이터 몰림 2배 조건, 200 rps

후보 인덱스의 첫 1분 측정이 p95 `2,094.53 ms`, p99 `2,185.07 ms`로 실패했다. 요청 누락과 오류는 없었지만 응답 시간 기준을 크게 넘었다. 최초 실패 지점에서 중단한다는 기준에 따라 같은 조건에서의 추가 반복 측정과 데이터 몰림 5배 조건은 실행하지 않았다.

| 데이터 조건 | 인덱스 상태 | 측정 시간 | p95 ms | p99 ms | 판정 |
| --- | --- | ---: | ---: | ---: | --- |
| 데이터 몰림 조건 | 후보 인덱스 | 10분 | 42.28 | 53.46 | 통과 |
| 데이터 몰림 2배 조건 | 후보 인덱스 | 1분 | 2,094.53 | 2,185.07 | 실패 |

두 행은 측정 시간이 달라 응답 시간을 같은 길이의 반복 실험처럼 직접 비교할 수는 없다. 다만 데이터 몰림 조건은 10분 동안 기준을 만족했고, 데이터 몰림 2배 조건은 첫 1분부터 기준을 크게 넘었다. 따라서 최초 실패 경계가 데이터 몰림 2배 조건이라는 판단에는 충분하다.

데이터 몰림 2배 조건에서도 후보 인덱스가 사용됐고 대부분 실제 테이블을 다시 읽지 않았다. 그런데 동시에 들어온 각 요청이 약 `34.1만 개`의 인덱스 항목을 반복해서 세면서 응답이 밀린 것으로 보인다. 요청 누락이나 기능 오류가 아니라 지연 시간만 크게 늘어난 결과이므로, 동시 집계 작업으로 DB 대기열이나 자원 사용량이 커졌을 가능성을 보여준다. 이번 측정에서는 DB CPU·대기 이벤트를 함께 수집하지 않았으므로 정확한 포화 지점과 원인을 확정하지는 않는다.

### 일반 데이터, 300 rps · 10분

현재 `develop` 코드만으로 `180,001건`을 처리했고 p95 `80.86 ms`, p99 `354.78 ms`, 요청 누락 `0`, 오류율 `0%`, 검사 성공률 `100%`로 통과했다. 과거 실패가 현재 코드에서 재현되지 않았으므로 후보 인덱스를 적용한 중복 측정은 하지 않았다.

### 일반 데이터, 300 rps 초과 경계

기본 데이터만 사용하고 현재 코드와 기존 인덱스를 그대로 측정했다. 후보 인덱스와 데이터 몰림 조건을 만들기 위한 추가 데이터는 적용하지 않았다.

| RPS | 측정 | p95 ms | p99 ms | 요청 누락 | 오류율 | 판정 |
| ---: | --- | ---: | ---: | ---: | ---: | --- |
| 350 | 1분 1회차 | 30.05 | 181.02 | 0 | 0% | 통과 |
| 350 | 1분 2회차 | 22.38 | 31.81 | 0 | 0% | 통과 |
| 350 | 1분 3회차 | 21.67 | 28.44 | 0 | 0% | 통과 |
| 375 | 1분 1회차 | 590.30 | 874.74 | 0 | 0% | 실패 |
| 375 | 1분 2회차 | 42.56 | 149.05 | 0 | 0% | 통과 |
| 375 | 1분 3회차 | 23.52 | 33.56 | 0 | 0% | 통과 |
| 400 | 1분 1회차 | 31.67 | 54.49 | 0 | 0% | 통과 |
| 400 | 1분 2회차 | 1,112.76 | 1,366.41 | 54 | 0% | 실패 |
| 400 | 1분 3회차 | 1,421.89 | 1,600.70 | 478 | 0% | 실패 |
| 350 | 10분 지속 | 1,713.57 | 1,917.48 | 6,646 | 0.0187% | 실패 |

`350 rps`는 짧은 1분 측정에서는 세 번 모두 통과했지만 10분 동안 유지하자 `210,001건`의 예정 요청 중 `203,355건`만 시작해 `6,646건`이 누락됐다. 시간이 지나면서 동시에 처리 중인 요청이 최대 VU `500`까지 쌓였고 응답 시간도 기준을 넘었다. 즉, 순간적으로 `350 rps`를 처리한 것과 10분 동안 계속 처리할 수 있는 것은 다르다.

`375 rps`는 가운데 값 기준으로는 통과하지만 한 회차가 실패해 변동 구간이다. `400 rps`는 3회 중 2회가 실패했으므로 반복 실패 지점이다. 따라서 이번 로컬 조건에서 확인한 경계는 아래와 같다.

- 지속 통과 확인: `300 rps · 10분`
- 단기 통과 확인: `350 rps · 1분`, 3회 모두 통과
- 변동 구간: `375 rps · 1분`, 2회 통과·1회 실패
- 반복 실패: `400 rps · 1분`, 1회 통과·2회 실패

`350 rps · 10분` 측정 전·중·후 PostgreSQL 컨테이너의 누적 블록 읽기는 모두 `0 B`였다. 처음 디스크에서 읽는 시간이 섞여 느려진 결과가 아니라, 워밍업된 상태에서도 요청이 처리 속도보다 빠르게 쌓인 결과로 해석한다. 다만 `301~349 rps`의 10분 측정은 하지 않았으므로 정확한 최대 지속 RPS를 하나의 숫자로 단정하지 않는다.

## 결과를 해석할 때의 한계

- 데이터 몰림 조건의 안정적인 통과는 후보 인덱스 4개를 적용한 결과다. 이 인덱스들은 Flyway 변경에 포함하지 않았으므로 현재 배포 상태의 성능을 뜻하지 않는다.
- 기존 인덱스만 사용한 1분 측정은 3회 중 1회가 p95와 p99 기준을 모두 넘었다. 가운데 값은 통과했지만 안정적인 통과 구간으로 보기는 어렵다.
- 후보 인덱스를 적용해도 요청 한 번에 약 `17.1만 개`의 인덱스 항목을 직접 센다. 한 대상에 몰린 데이터가 증가할수록 확인할 항목도 함께 늘어나는 구조는 그대로다.
- 데이터 몰림 조건에서도 `275 rps`부터 회차별 차이가 커지고 `300 rps`에서 반복 실패했다. 인덱스가 반복 집계 자체를 제거한 것은 아니다.
- 로컬 Docker, 단일 대상 사용자, 워밍업된 캐시, 읽기 부하 중심 조건에서 측정했다. 여러 사용자의 실제 트래픽과 운영 장비에서도 같은 결과가 나온다고 보장할 수 없다.
- 후보 인덱스 4개는 데이터 몰림 조건 기준 약 `479 MB`를 추가로 사용한다. 댓글·조회·좋아요·구독을 저장할 때 생기는 쓰기 성능 저하는 아직 측정하지 않았다.
- 일반 데이터도 단일 대상 사용자와 로컬 장비에서 측정했다. 실제 사용자가 여러 계정에 분산되어 요청하는 운영 환경과 부하 모양이 다르므로 이 숫자는 운영 보장값이 아니다.
- 서비스가 막 공개된 시점이라 실제 사용자 요청 데이터가 충분하지 않다. 현재 RPS를 실제 사용자 수로 바꾸어 추정하지 않고, 운영 로그가 쌓인 뒤 이 API의 최고 RPS와 p95·p99를 같은 기준으로 비교한다.
