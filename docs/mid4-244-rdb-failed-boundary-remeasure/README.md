# MID4-244 RDB 실패 경계 후속 재측정

> 이전 작업: [MID4-227 노출 상태 적용 전후 재측정](../mid4-227-rdb-bottleneck-remeasure/README.md) · [활동 내역 성능 문서 통합 안내](../activity-history-performance-guide.md)

## 한눈에 보는 결론

- 이전에 통과한 조건은 다시 측정하지 않았다. MID4-227의 `fan-out 200 rps · 1분`과 MID4-206의 `일반 300 rps · 10분` 실패 조건부터 확인했다.
- 일반 데이터의 `300 rps · 10분`은 현재 `develop` 코드만으로 통과했다. 따라서 이 조건에는 후보 인덱스를 적용한 중복 측정을 하지 않았다.
- 연결 데이터가 한곳에 몰린 1배 조건에서는 활성 데이터만 담고 집계에 필요한 ID까지 가진 부분 커버링 인덱스(partial covering index)가 응답을 안정화했다.
- 같은 연결 데이터를 2배로 늘리자 후보 인덱스를 적용해도 `p95 2,094.53 ms`, `p99 2,185.07 ms`로 실패했다. 계획대로 최초 실패에서 중단해 5배 조건은 실행하지 않았다.
- 인덱스는 실제 테이블을 다시 읽는 횟수와 메모리 버퍼 사용량을 줄였다. 다만 결과마다 댓글·조회·구독 수를 세는 하위 조회(subquery)는 유지되므로, 연결 데이터가 늘면 인덱스 안에서 확인할 항목 수도 함께 늘어난다.
- 이번 인덱스는 성능 실험용이며 운영 배포용 DB 변경(Flyway migration)에는 넣지 않았다. 네 인덱스의 합계 크기가 약 `479 MB`이고 쓰기 비용을 별도로 검증하지 않았기 때문이다.

## 왜 실패 조건만 측정했나

이미 통과한 조건을 같은 코드로 다시 실행해도 새로운 판단 근거가 늘지 않는다. 이번 작업은 아래 두 실패 기록에서 시작했다.

| 출발점 | 이전 결과 | 이번 확인 방식 |
| --- | --- | --- |
| MID4-227 데이터 몰림 `200 rps · 1분` | p95 `379.23 ms`로 실패 | 현재 코드와 부분 인덱스 후보를 같은 1배 데이터에서 비교 |
| MID4-206 일반 `300 rps · 10분` | p95 `1,692.74 ms`, p99 `1,934.22 ms`, 요청 누락 `1,159건` | 현재 코드로 먼저 재현하고, 실패할 때만 후보 적용 |

MID4-227에서 통과한 `150 rps` 이하, 제외 데이터(exclusion), 읽기·쓰기 혼합(mixed) 조건과 MID4-206에서 통과한 `250 rps` 이하는 재측정 대상에서 제외했다.

1배는 MID4-227 재측정에 사용한 동일 데이터 DB를 재사용했고, 2배와 일반 조건은 각각 새 DB에 기본 데이터를 다시 적재했다. 같은 배수의 현재 인덱스와 후보 인덱스 SQL은 같은 DB 데이터를 사용했고, 각 SQL을 따로 워밍업한 뒤 측정했다. SQL 실행 순서는 현재 인덱스, 후보 인덱스 순이다. 1배 API는 후보를 먼저 측정한 뒤 후보 인덱스를 제거하고 현재 상태를 측정했으며, 양쪽 모두 별도의 워밍업을 수행했다.

## 비교한 인덱스 후보

활성 데이터만 인덱스에 넣어 크기를 줄이고, `count(id)`에 필요한 ID를 함께 저장해 실제 테이블을 다시 방문하는 비용을 줄이는 후보다.

```sql
CREATE INDEX IF NOT EXISTS idx_perf_comments_active_article_cover
    ON comments(article_id) INCLUDE(id)
    WHERE visibility_status = 'ACTIVE';

CREATE INDEX IF NOT EXISTS idx_perf_article_views_active_article_cover
    ON article_views(article_id) INCLUDE(id)
    WHERE visibility_status = 'ACTIVE';

CREATE INDEX IF NOT EXISTS idx_perf_comment_likes_active_comment_cover
    ON comment_likes(comment_id) INCLUDE(id)
    WHERE visibility_status = 'ACTIVE';

CREATE INDEX IF NOT EXISTS idx_perf_subscriptions_active_interest_cover
    ON subscriptions(interest_id) INCLUDE(id)
    WHERE visibility_status = 'ACTIVE';
```

1배 데이터에서 확인한 크기는 `comments 177 MB`, `article_views 144 MB`, `comment_likes 132 MB`, `subscriptions 26 MB`다.

대표 실행계획에서 디스크 읽기(shared read)는 모두 `0`이었다. 워밍업 뒤 메모리에 올라온 같은 조건을 비교했으므로 디스크 최초 읽기 시간이 결과에 섞이지 않았다.

후보 인덱스를 사용한 집계는 대부분 인덱스만 읽는 방식(Index Only Scan)으로 바뀌었다. 하지만 최근 조회 기사 하위 조회는 결과 10건마다 두 집계를 실행하고, 구독 관심사 하위 조회는 결과 50건마다 집계를 실행했다. 2배 데이터에서 한 번의 집계가 읽는 행도 기사 조회 약 `20,003건`, 관심사 구독 약 `2,011건`으로 늘었다.

2배 데이터 실행계획 원문에 기록된 집계 단계는 다음과 같다. 현재 인덱스의 `Index Scan`에는 `Heap Fetches` 항목이 따로 표시되지 않으며 실제 테이블을 읽는다.

| 집계 단계 | 한 번에 처리한 행 | 반복 횟수 | 현재 → 부분 인덱스 버퍼 | 부분 인덱스 Heap Fetches |
| --- | ---: | ---: | ---: | ---: |
| 최근 작성 댓글의 좋아요 수 | 2,001 | 10 | 489 → 170 | 0 |
| 최근 좋아요한 댓글의 좋아요 수 | 2 | 10 | 50 → 31 | 0 |
| 최근 조회 기사의 댓글 수 | 2,002 | 10 | 3,520 → 180 | 10 |
| 최근 조회 기사의 조회 수 | 20,003 | 10 | 4,299 → 1,250 | 0 |
| 구독 관심사의 구독자 수 | 2,011 | 50 | 2,969 → 756 | 0 |

실제 실행 SQL과 PostgreSQL 실행계획 원문은 [SQL과 실행계획 원문](sql-and-explain.md)에 코드 블록으로 기록했다.

### 연결 데이터 2배, 200 rps

부분 인덱스 후보의 첫 1분 측정이 p95 `2,094.53 ms`, p99 `2,185.07 ms`로 실패했다. 요청 누락과 오류는 없었지만 응답 시간 기준을 크게 넘었다. 최초 실패 지점에서 중단한다는 기준에 따라 같은 조건의 추가 반복과 5배 데이터 측정은 실행하지 않았다.

### 일반 데이터, 300 rps · 10분

현재 `develop` 코드만으로 `180,001건`을 처리했고 p95 `80.86 ms`, p99 `354.78 ms`, 요청 누락 `0`, 오류율 `0%`, 검사 성공률 `100%`로 통과했다. 과거 실패가 현재 코드에서 재현되지 않았으므로 부분 인덱스를 적용한 중복 측정은 하지 않았다.

## 판단과 다음 작업

부분 인덱스는 1배 데이터의 불안정한 실패 경계를 안정화하고, 2배 데이터에서도 SQL 한 번의 읽기 비용을 약 19~57% 줄였다. 따라서 “실제 테이블을 다시 방문하는 비용을 줄인다”는 목적에는 효과가 있었다.

이번 작업에서는 SQL 구조를 별도로 변경하지 않는다. 커버링 인덱스를 적용하면 `count(id)`가 실제 테이블 대신 인덱스만 읽는 방식(Index Only Scan)으로 바뀌지만, 개수를 세기 위해 조건에 맞는 인덱스 항목을 확인하는 일은 남는다. 2배 데이터 실패는 커버링 인덱스가 사용되지 않은 결과가 아니라, 커버링 인덱스를 사용한 상태에서도 확인할 항목이 늘어난 결과다.

따라서 이번 판단 범위는 부분 커버링 인덱스의 효과와 한계를 확인하는 데까지다. SQL 변경안이나 별도의 조회용 데이터(Read Model)는 이 작업의 후속 계획에 포함하지 않는다.

운영 인덱스로 확정하기 전에는 아래도 추가로 확인해야 한다.

- 약 `479 MB`의 추가 저장 공간이 운영 DB에서 허용되는가
- 댓글·조회·좋아요·구독 쓰기 성능이 새 인덱스로 얼마나 느려지는가
- 네 인덱스를 모두 둘지, 효과가 큰 기사 조회와 구독 집계만 선택할지
