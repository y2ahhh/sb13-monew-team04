# MID4-244 RDB 실패 경계 후속 재측정

> 이전 작업: [MID4-227 노출 상태 적용 전후 재측정](../mid4-227-rdb-bottleneck-remeasure/README.md) · [활동 내역 성능 문서 통합 안내](../activity-history-performance-guide.md)

## 한눈에 보는 결론

- 최초 인덱스 비교는 MID4-227의 `데이터 몰림(fan-out) 200 rps · 1분`과 MID4-206의 `일반 300 rps · 10분` 실패 조건부터 확인했다. 이후 데이터 몰림 조건의 처리량 한계 측정은 요청대로 `200 rps`부터 시작해 위로 올렸다.
- 일반 데이터의 `300 rps · 10분`은 현재 `develop` 코드만으로 통과했다. 따라서 이 조건에는 후보 인덱스를 적용한 중복 측정을 하지 않고, 아직 확인하지 않은 `300 rps` 초과 구간부터 측정했다.
- 좋아요·댓글·조회·구독 데이터를 특정 댓글·기사·관심사에 집중시킨 데이터 몰림 조건에서는 부분 커버링 인덱스(partial covering index) 4개가 응답을 안정화했다. 이 후보 인덱스들은 활성 데이터만 담고 집계에 필요한 ID도 함께 저장한다.
- 기사 조회 수 집계를 별도로 확인한 결과, JPQL을 `COUNT(*)`로 바꾸면 `INCLUDE(id)` 없는 ACTIVE 부분 인덱스도 `Index Only Scan`, `Heap Fetches 0`으로 동작했다. 해당 인덱스는 `76 MB`로 `INCLUDE(id)`를 둔 `144 MB`보다 작았지만 코드와 Flyway에는 반영하지 않았다.
- 같은 데이터 몰림 조건에서 요청량을 올린 결과 `250 rps`는 3회 모두 통과했고, `275 rps`는 가운데 값 기준으로 통과했지만 한 회차가 실패했으며, `300 rps`는 3회 모두 실패했다. 따라서 `275 rps`는 통과 지점으로 기록하되 항상 같은 응답 시간을 보장하는 안정 구간으로 보지는 않는다.
- 특정 대상에 추가한 좋아요·댓글·조회·구독 건수를 데이터 몰림 조건의 2배로 늘리자 후보 인덱스를 적용해도 `p95 2,094.53 ms`, `p99 2,185.07 ms`로 실패했다. 계획대로 최초 실패에서 중단해 데이터 몰림 5배 조건은 실행하지 않았다.
- 일반 데이터에서는 `350 rps`가 1분 3회를 모두 통과했고, `375 rps`는 2회 통과·1회 실패, `400 rps`는 1회 통과·2회 실패였다. 그러나 `350 rps · 10분`은 시간이 지나면서 밀려 실패했다. 현재 확인한 지속 통과 지점은 기존 `300 rps · 10분`이고, `350 rps`는 짧게 처리할 수 있어도 계속 유지할 수 있는 값은 아니다.
- 인덱스는 실제 테이블을 다시 읽는 횟수와 메모리 버퍼 사용량을 줄였다. 다만 결과마다 댓글·조회·구독 수를 세는 하위 조회(subquery)는 유지되므로, 한 대상에 몰린 데이터가 늘면 인덱스 안에서 확인할 항목 수도 함께 늘어난다.
- 후보 인덱스 4개는 성능 실험용이며 운영 배포용 DB 변경(Flyway migration)에는 넣지 않았다. 합계 크기가 약 `479 MB`이고 쓰기 비용을 별도로 검증하지 않았기 때문이다.

## 왜 실패 조건만 측정했나

이미 통과한 조건을 같은 코드로 다시 실행해도 새로운 판단 근거가 늘지 않는다. 이번 작업은 아래 두 실패 기록에서 시작했다.

| 출발점 | 이전 결과 | 이번 확인 방식 |
| --- | --- | --- |
| MID4-227 데이터 몰림 `200 rps · 1분` | p95 `379.23 ms`로 실패 | 현재 코드에서 기존 인덱스와 후보 인덱스를 같은 데이터 몰림 조건으로 비교 |
| MID4-206 일반 `300 rps · 10분` | p95 `1,692.74 ms`, p99 `1,934.22 ms`, 요청 누락 `1,159건` | 현재 코드로 먼저 재현하고, 실패할 때만 후보 적용 |

MID4-227에서 통과한 `150 rps` 이하, 제외 데이터(exclusion), 읽기·쓰기 혼합(mixed) 조건과 MID4-206에서 통과한 `250 rps` 이하는 재측정 대상에서 제외했다.

최초 인덱스 비교의 데이터 준비 방식은 다음과 같다. 데이터 몰림 조건은 MID4-227 재측정 DB를 재사용했다. 데이터 몰림 2배 조건과 일반 조건은 각각 새 DB에 기본 데이터를 다시 적재했다.

같은 SQL을 기존 인덱스만 사용한 상태와 후보 인덱스를 추가한 상태에서 동일한 데이터로 비교했다. 각 상태의 SQL을 따로 워밍업했고, 기존 인덱스 다음 후보 인덱스 순으로 실행했다. API는 후보 인덱스를 추가한 상태를 먼저 측정했다. 이후 후보 인덱스를 제거하고 기존 인덱스만 있는 상태를 측정했으며, 두 상태 모두 별도로 워밍업했다.

데이터 몰림 조건의 요청량 상향 측정은 기존 DB를 재사용하지 않고 아래 순서로 다시 준비했다.

1. 전용 Docker 프로젝트의 DB와 볼륨을 제거하고 새로 생성했다.
2. 애플리케이션 스키마를 적용하고 `SEED_SCALE=10m` 데이터를 새로 적재했다.
3. MID4-227과 동일한 수량으로 데이터 몰림 조건을 만들기 위한 데이터를 추가하고 실제 건수를 확인했다.
4. 부분 커버링 인덱스 4개를 적용한 뒤 `ANALYZE`를 실행했다.
5. 디버그 모드에서 API를 한 번 호출해 실제 SQL이 실행되는지 확인했다.
6. 성능 모드로 애플리케이션을 다시 시작하고 `1 VU · 1분` 워밍업을 실행했다.
7. 이미 통과한 더 낮은 RPS는 제외하고 `200 rps`부터 요청량을 올렸다. 각 RPS는 1분씩 3회 실행하고 사이에 30초를 두었다.

`200~250 rps` 측정 후 같은 DB와 인덱스는 유지했다. 애플리케이션만 성능 모드로 다시 시작하고 `1 VU · 1분` 워밍업을 다시 수행한 뒤 `275 rps`, `300 rps`를 이어서 측정했다.

일반 데이터의 처리량 한계는 데이터 몰림 실험과 분리해 아래 순서로 측정했다.

1. 전용 Docker 프로젝트의 DB와 볼륨을 제거하고 `SEED_SCALE=10m` 기본 데이터를 새로 적재했다.
2. 데이터 몰림·제외 조건을 만들기 위한 추가 데이터와 후보 인덱스는 적용하지 않았다.
3. 디버그 모드에서 API를 한 번 호출해 실제 SQL을 확인했다.
4. 애플리케이션을 성능 모드로 다시 시작하고 `1 VU · 1분` 워밍업을 실행했다.
5. 이미 10분 통과한 `300 rps`는 반복하지 않고 `350 rps`, `400 rps`를 각각 1분 3회 측정했다. `400 rps`가 2회 실패한 시점에서 `450 rps`, `500 rps`는 실행하지 않았다.
6. `350 rps`와 `400 rps` 사이의 `375 rps`는 새 DB와 같은 준비 순서로 1분 3회 측정했다.
7. 1분 3회를 모두 통과한 `350 rps`는 같은 기본 데이터 DB를 유지하고 애플리케이션 재시작과 워밍업을 다시 한 뒤 10분 동안 확인했다.

## 비교한 인덱스 후보

활성 데이터만 인덱스에 넣어 크기를 줄이고, `count(id)`에 필요한 ID를 함께 저장해 실제 테이블을 다시 방문하는 비용을 줄이는 후보 인덱스다.

```sql
CREATE INDEX IF NOT EXISTS idx_perf_comments_active_article_cover
    ON comments(article_id) INCLUDE(id)
    WHERE visibility_status = 'ACTIVE';

CREATE INDEX IF NOT EXISTS idx_perf_article_views_active_article_cover
    ON article_views(article_id) INCLUDE(id)
    WHERE visibility_status = 'ACTIVE';

CREATE INDEX IF NOT EXISTS idx_perf_comment_likes_active_comment_cover
    ON comment_likes(comment_id) INCLUDE(id)
    WHERE visibility_status = 'ACTIVE';

CREATE INDEX IF NOT EXISTS idx_perf_subscriptions_active_interest_cover
    ON subscriptions(interest_id) INCLUDE(id)
    WHERE visibility_status = 'ACTIVE';
```

데이터 몰림 조건에서 측정한 후보 인덱스 크기는 `comments 177 MB`, `article_views 144 MB`, `comment_likes 132 MB`, `subscriptions 26 MB`다.

대표 실행계획에서 디스크 읽기(shared read)는 모두 `0`이었다. 워밍업 뒤 메모리에 올라온 같은 조건을 비교했으므로 처음 디스크에서 읽는 시간이 결과에 섞이지 않았다.

후보 인덱스를 사용한 집계는 대부분 인덱스만 읽는 방식(Index Only Scan)으로 바뀌었다. 하지만 최근 조회 기사 하위 조회는 결과 10건마다 두 집계를 실행하고, 구독 관심사 하위 조회는 결과 50건마다 집계를 실행했다. 데이터 몰림 2배 조건에서 집계 1회가 확인한 행 수는 기사별 조회 수 계산 약 `20,003건`, 관심사별 구독자 수 계산 약 `2,011건`이었다.

### 데이터 몰림 조건별 집계 항목 수

후보 인덱스를 사용한 대표 실행계획의 `rows × loops`를 계산하면, API 요청 한 번이 집계 때문에 확인한 인덱스 항목 수를 비교할 수 있다. 이 값은 SQL 실행 시간 자체가 아니라 하위 조회가 반복해서 센 데이터 양이다.

| --- | ---: | ---: | ---: | ---: | ---: |
| 최근 작성 댓글의 좋아요 수 | 1,001 × 10 | 10,010 | 2,001 × 10 | 20,010 | 0 → 0 |
| 최근 좋아요한 댓글의 좋아요 수 | 2 × 10 | 20 | 2 × 10 | 20 | 0 → 0 |
| 최근 조회 기사의 댓글 수 | 1,002 × 10 | 10,020 | 2,002 × 10 | 20,020 | 0 → 10 |
| 최근 조회 기사의 조회 수 | 10,003 × 10 | 100,030 | 20,003 × 10 | 200,030 | 0 → 0 |
| 구독 관심사의 구독자 수 | 1,011 × 50 | 50,550 | 2,011 × 50 | 100,550 | 0 → 0 |

특정 대상에 추가한 좋아요·댓글·조회·구독 건수를 데이터 몰림 조건의 2배로 늘리자 요청 한 번에 확인한 인덱스 항목도 약 `17.1만 개`에서 `34.1만 개`로 거의 2배가 됐다. `200 rps`가 계속 들어온다고 단순 환산하면 초당 약 `3,413만 개`에서 `6,813만 개`를 확인하는 양이다. 대부분 `Index Only Scan`과 `Heap Fetches 0`을 달성했으므로 실제 테이블 재방문은 줄었지만, 정확한 개수를 구하기 위해 조건에 맞는 인덱스 항목을 세는 일은 사라지지 않았다.

각 조회 이름을 선택하면 실제 실행 SQL과 PostgreSQL 실행계획 원문을 확인할 수 있다.

| 기존 인덱스 | 1분 1회차 | 116.76 | 149.70 | 0 | 0% | 통과 |
| 기존 인덱스 | 1분 2회차 | 164.24 | 240.89 | 0 | 0% | 통과 |

기존 인덱스는 3회 가운데 값이 p95 `164.24 ms`, p99 `240.89 ms`라서 가운데 값 기준으로는 통과했다. 그러나 3회차가 기준을 넘었으므로 안정적으로 통과했다고 보기는 어렵다. 후보 인덱스는 1분 3회와 10분 지속 측정을 모두 통과했다.

이번 측정에서 세 번 모두 통과한 가장 높은 요청량은 `250 rps`였다. `275 rps`는 가운데 값 p95 `148.66 ms`, p99 `280.41 ms`가 기준 안이고 3회 중 2회가 통과했으므로 가운데 값 기준 통과 지점이다. 다만 한 회차는 응답 시간과 요청 누락 기준을 넘었으므로 안정적인 보장값은 아니다. `300 rps`는 세 회차 모두 실패했다. 따라서 `250 rps`는 안정 통과, `275 rps`는 변동이 있는 통과, `300 rps`는 반복 실패로 구분한다.

MID4-227과 같은 데이터 몰림 조건이 적용됐는지 추가 건수를 확인했다.

| 확인 항목 | 건수 |
| --- | ---: |
| 최근 댓글 10개의 추가 좋아요 | 10,000 |
| 최근 기사 10개의 추가 댓글 | 10,000 |
| 최근 기사 10개의 추가 조회 | 100,000 |
| 관심사 50개의 추가 구독 | 50,000 |

첫 워밍업은 p95 `56.71 ms`, p99 `145.64 ms`였고, 상향 측정 재개 전 워밍업은 p95 `48.17 ms`, p99 `152.06 ms`였다. 두 워밍업 모두 오류와 요청 누락이 없었다. PostgreSQL 컨테이너의 누적 블록 읽기는 `200 rps` 시작 전부터 `300 rps` 종료 후까지 `258 kB`로 같았다. 이 값만으로 모든 계층의 캐시를 증명할 수는 없지만, 부하 측정 중 새 디스크 읽기가 관찰되지 않았다는 근거다. SQL 실행계획에서도 워밍업 후 `shared read=0`을 확인했으므로 이번 결과에는 처음 디스크에서 읽는 시간이 섞이지 않은 것으로 본다.

### 데이터 몰림 2배 조건, 200 rps

후보 인덱스의 첫 1분 측정이 p95 `2,094.53 ms`, p99 `2,185.07 ms`로 실패했다. 요청 누락과 오류는 없었지만 응답 시간 기준을 크게 넘었다. 최초 실패 지점에서 중단한다는 기준에 따라 같은 조건에서의 추가 반복 측정과 데이터 몰림 5배 조건은 실행하지 않았다.

| 데이터 조건 | 인덱스 상태 | 측정 시간 | p95 ms | p99 ms | 판정 |
| --- | --- | ---: | ---: | ---: | --- |
| 데이터 몰림 조건 | 후보 인덱스 | 10분 | 42.28 | 53.46 | 통과 |
| 데이터 몰림 2배 조건 | 후보 인덱스 | 1분 | 2,094.53 | 2,185.07 | 실패 |

두 행은 측정 시간이 달라 응답 시간을 같은 길이의 반복 실험처럼 직접 비교할 수는 없다. 다만 데이터 몰림 조건은 10분 동안 기준을 만족했고, 데이터 몰림 2배 조건은 첫 1분부터 기준을 크게 넘었다. 따라서 최초 실패 경계가 데이터 몰림 2배 조건이라는 판단에는 충분하다.

데이터 몰림 2배 조건에서도 후보 인덱스가 사용됐고 대부분 실제 테이블을 다시 읽지 않았다. 그런데 동시에 들어온 각 요청이 약 `34.1만 개`의 인덱스 항목을 반복해서 세면서 응답이 밀린 것으로 보인다. 요청 누락이나 기능 오류가 아니라 지연 시간만 크게 늘어난 결과이므로, 동시 집계 작업으로 DB 대기열이나 자원 사용량이 커졌을 가능성을 보여준다. 이번 측정에서는 DB CPU·대기 이벤트를 함께 수집하지 않았으므로 정확한 포화 지점과 원인을 확정하지는 않는다.

### 일반 데이터, 300 rps · 10분

현재 `develop` 코드만으로 `180,001건`을 처리했고 p95 `80.86 ms`, p99 `354.78 ms`, 요청 누락 `0`, 오류율 `0%`, 검사 성공률 `100%`로 통과했다. 과거 실패가 현재 코드에서 재현되지 않았으므로 후보 인덱스를 적용한 중복 측정은 하지 않았다.

- 지속 통과 확인: `300 rps · 10분`
- 단기 통과 확인: `350 rps · 1분`, 3회 모두 통과
- 변동 구간: `375 rps · 1분`, 2회 통과·1회 실패
- 반복 실패: `400 rps · 1분`, 1회 통과·2회 실패

## 데이터 몰림 조건과 일반 RPS 결과를 해석할 때의 한계

- 데이터 몰림 조건의 안정적인 통과는 후보 인덱스 4개를 적용한 결과다. 이 인덱스들은 Flyway 변경에 포함하지 않았으므로 현재 배포 상태의 성능을 뜻하지 않는다.
- 기존 인덱스만 사용한 1분 측정은 3회 중 1회가 p95와 p99 기준을 모두 넘었다. 가운데 값은 통과했지만 안정적인 통과 구간으로 보기는 어렵다.
- 후보 인덱스를 적용해도 요청 한 번에 약 `17.1만 개`의 인덱스 항목을 직접 센다. 한 대상에 몰린 데이터가 증가할수록 확인할 항목도 함께 늘어나는 구조는 그대로다.
- 데이터 몰림 조건에서도 `275 rps`부터 회차별 차이가 커지고 `300 rps`에서 반복 실패했다. 인덱스가 반복 집계 자체를 제거한 것은 아니다.
- 로컬 Docker, 단일 대상 사용자, 워밍업된 캐시, 읽기 부하 중심 조건에서 측정했다. 여러 사용자의 실제 트래픽과 운영 장비에서도 같은 결과가 나온다고 보장할 수 없다.
- 후보 인덱스 4개는 데이터 몰림 조건 기준 약 `479 MB`를 추가로 사용한다. 댓글·조회·좋아요·구독을 저장할 때 생기는 쓰기 성능 저하는 아직 측정하지 않았다.
- 일반 데이터도 단일 대상 사용자와 로컬 장비에서 측정했다. 실제 사용자가 여러 계정에 분산되어 요청하는 운영 환경과 부하 모양이 다르므로 이 숫자는 운영 보장값이 아니다.
- 서비스가 막 공개된 시점이라 실제 사용자 요청 데이터가 충분하지 않다. 현재 RPS를 실제 사용자 수로 바꾸어 추정하지 않고, 운영 로그가 쌓인 뒤 이 API의 최고 RPS와 p95·p99를 같은 기준으로 비교한다.

## 판단과 다음 작업

후보 인덱스를 적용하자 데이터 몰림 조건의 `200 rps · 1분` 측정은 3회 모두 통과했고, 10분 측정도 통과했다. 데이터 몰림 2배 조건에서도 효과가 확인된 세 조회의 SQL 실행 시간을 약 19~57% 줄였다. 따라서 “실제 테이블을 다시 방문하는 비용을 줄인다”는 목적에는 효과가 있었다.

데이터 몰림 조건의 요청량 상향 측정에서는 `250 rps`까지 안정적으로 통과했고 `275 rps`는 가운데 값 기준으로 통과했지만 결과가 흔들렸으며, `300 rps`에서 반복 실패했다. 요청량이 늘면 요청마다 약 `17.1만 개`를 세는 작업이 동시에 쌓이는 현재 구조의 처리량 한계가 다시 나타난다.

일반 데이터는 현재 코드에서 `300 rps · 10분`을 통과했다. `350 rps`는 1분 3회에는 통과했지만 10분에는 실패했으므로, 현재 확인된 지속 통과 기준은 `300 rps`다. 더 높은 지속 처리량이 요구되기 전까지 조회 구조를 미리 복잡하게 바꾸지는 않는다.

이번 작업에서는 SQL 구조를 변경하지 않았다. 현재 JPQL의 `COUNT(별칭)`은 Hibernate에서 `count(별칭.id)`로 변환되므로 후보 인덱스의 `INCLUDE(id)`가 Index Only Scan에 필요하다. 후속 기사 조회 확인에서는 JPQL을 `COUNT(*)`로 바꾸면 `count(*)`가 생성됐고, 이 경우 `INCLUDE(id)` 없는 ACTIVE 부분 인덱스도 Index Only Scan으로 동작했다. 다만 개수를 세기 위해 조건에 맞는 인덱스 항목을 확인하는 일은 두 방식 모두 남는다.

기사 조회 수 10,003건 조건에서 `COUNT(*)`와 `INCLUDE(id)` 없는 부분 인덱스 조합은 `76 MB`, `shared hit 13`, 실행 시간 중앙값 `0.369 ms`였다. `INCLUDE(id)`를 둔 인덱스는 `144 MB`, `shared hit 65`, `0.493 ms`였다. 이 실행 시간은 로컬 단일 조건의 보조 결과이며, 더 작은 인덱스와 heap 접근이 없다는 사실을 주된 판단 근거로 사용한다. 상세 결과는 [최근 조회 기사 실행계획](recent-article-views.md#count와-includeid-비교)에 기록했다.

데이터 몰림 2배 조건의 실패는 후보 인덱스가 사용되지 않은 결과가 아니라, 후보 인덱스를 사용한 상태에서도 확인할 항목이 늘어난 결과다.

따라서 이번 판단 범위는 부분 커버링 인덱스의 효과와 한계, 현재 일반 조회의 처리량 경계를 확인하는 데까지다. SQL은 별도로 변경하지 않았고, 카운터 테이블이나 별도의 조회용 데이터(Read Model)도 구현하지 않았다.

카운터 테이블(counter table)은 댓글 수·조회 수·구독자 수처럼 자주 세는 값을 별도 테이블에 미리 저장하는 방식이다. 같은 값을 매번 다시 세는 비용은 줄지만, 원본 데이터가 바뀔 때 숫자도 정확히 맞추고 오류가 났을 때 복구하는 로직이 필요하다. 이는 중복 데이터를 두는 역정규화(denormalization)이므로 초기 구조의 기본 선택이 아니라, 개수 계산이 실제 병목이고 요구 처리량이 현재 한계를 넘을 때 검토한다.

MongoDB에 만든 조회용 데이터(Read Model)는 개수 하나가 아니라 활동 내역 조회 전체를 RDB와 분리해 독립적으로 확장해야 할 때 검토한다. 개수 계산만 문제라면 카운터 테이블이 더 작은 변경이고, 조회 전체의 저장·확장 방식이 문제라면 MongoDB가 더 넓은 대안이다. 둘 다 실제 운영 요청량과 목표 응답 시간이 확인된 뒤 선택한다.

운영 인덱스로 확정하기 전에는 아래도 추가로 확인해야 한다.

- 약 `479 MB`의 추가 저장 공간이 운영 DB에서 허용되는가
- 댓글·조회·좋아요·구독 쓰기 성능이 새 인덱스로 얼마나 느려지는가
- 네 인덱스를 모두 둘지, 효과가 큰 기사 조회와 구독 집계만 선택할지
